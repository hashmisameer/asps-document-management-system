## What this is

**ASPS-DMS** is an internal document management system for ASPS International,
a garment manufacturer in Noida. About 550 employees, ~470 active. HR collects
a fixed checklist of nine documents from each employee (appointment letter, bio
data form, Aadhaar and PAN cards, PF form / Form 11, ESIC form, payment of
gratuity, Form 16, confirmation letter), each with a deadline counted from the
joining date. Documents are uploaded as PDFs generated by another in-house
application, **MMC**, or as scans. The company's forms need two signatures - the
employee's and an HR authoriser's - and the ESIC form needs the employee's
photograph. The DMS stamps those onto the PDFs.

The problem it solves: paperwork that was chased by hand and signed by hand,
with nobody able to say what was outstanding. Now the checklist says what is
owed, a daily email attaches the overdue list as a spreadsheet, and signatures
are stamped onto uploaded forms automatically from per-type templates.

**Who uses it:** three roles. `HR` (uploads, chases, signs), `ADMIN` (HR plus
templates, user management, adding late joiners), `VIEWER` (read only). Five
accounts in all, created by self-registration (capped at 5; first is Admin) or
`npm run user:add`. The owner is Sameer Hashmi, who also runs the server.

## Decisions that look odd without their reason

**Stamping on upload with no approval step** (commit `03348f3`). When a
document is uploaded and its type has a template matching the file, the
signatures are stamped there and then: the employee's signature from their
record, the uploader's own "My signature" in the HR box, the photograph on the
ESIC form. HR does not open an editor or approve. Why: the employee's signature
comes from MMC's folder by employee code, and MMC itself stamps from that folder
with no approval; a wrong signature is a wrong file in MMC's folder, MMC's
mistake to fix, not a question for HR. What is never done is _guessed at_: a box
is left alone when something is already in it (the occupancy check), when the
image it needs is not on file, when no template matches, when the file is a
JPG/PNG scan, or when the identity check failed. Anything left alone sends the
document to `ReviewRequired` for HR. Every decision is a row in
`dbo.StampDecisions`. `AUTO_STAMP=report` (the default) decides and records
without stamping - the office is running that trial now; `AUTO_STAMP=stamp`
stamps. `npm run auto-stamp -- --report` prints the decisions; `-- --backlog`
decides about documents stuck from before this existed.

**Only the ESIC form is auto-stamped** (`AUTO_STAMP_TYPES=ESIC_FORM`, since
2026-09-22). MMC now prints the employee's signature and the HR stamp on every
form it generates _except_ the ESIC form. The application did not know that,
saw the box as empty - MMC's signature sits just outside it - and stamped the
employee's signature a second time on 26 PF and gratuity forms. So stamping on
upload is confined to a list of document codes; every other type is decided
`NotInList` (recorded once, nothing read, not a failure, nothing on the
checklist) and goes to `ReviewRequired` for HR. **Missing or empty list = no
type is stamped.** Those older documents are NOT auto-skipped: some are from
before MMC printed signatures. `npm run unstamp` took the 26 back (placements
and processed file removed through `removeStamp`, the editor's own path;
status `Skipped`; audit entry with the reason; refuses anything a person
placed).

**Deciding again when the image arrives later** (2026-09-22). A document was
stamped only at upload; a signature or photograph that reached the record
afterwards never went on (document 96: Manual photo on 15 Sept, signature on
the pad on 16 Sept, never stamped). Now every save of an employee's signature
or photograph - MMC pickup, hand upload, pad - runs `redecideForEmployee`
(stamp mode, listed types, uploader's name, 250 ms apart), and
`npm run auto-stamp -- --redecide --type ESIC_FORM [--dry-run]` does it for a
type's backlog (~500 ESIC forms decided in report mode). **Everything already
on a document is kept** - Automatic or Manual, rectangle, method, signer - and
only roles missing from a page are added (`decide()` takes `existing`; the
`keep` box action). The MMC attach path passes `{ redecide: false }` to
`uploadSignature` so the watcher's own re-decide is the only one. A kept HR
box makes the run act as its signer; no signature on that account = document
left alone with the reason. Overlap guard: a template box more than a tenth
under a hand-placed box is left alone. `applyPlacements` does not delete the
previous processed file when it writes a new one (pre-existing; a small leak).

**Several saved templates of one shape.** Templates saved before shape
matching (pre-18 Sept) were keyed on exact size, so one shape can hold several.
The stamper uses the **newest** saved template per shape and only that one
(`chooseTemplate` in `stampCheck.service.ts`; boxes collected by
`exactVariantKey`, never by the rounded `variantKey`). The Templates screen and
`--list` say how many a shape holds. Until 2026-09-22 the stamper collected
every one of them - the bug that would have doubled signatures on its own had
MMC's not got there first.

**A template matches by page SHAPE, not size** (commit `0d29de2`). The
generated forms come out at ~20 slightly different point sizes for one document
type; keyed on exact size that was 82 templates for 15 forms. Boxes were always
stored as 0-1 fractions of the page, so size never mattered to the stamper. A
template now covers: page count (exact) + orientation + aspect ratio within 1%.
A4 (1.414) and Letter (1.294) are deliberately _different_ shapes - "a box in
the wrong place is worse than a document HR has to sign by hand". Existing
templates were kept working with no migration: the shape is computed on read
from the sample size each row already stores. `npm run stamp-check -- --shapes`
and `-- --list` show how many templates a type needs and which shapes lack one.

**The joining-date rule** (commit `08f7f86`). HR may create an employee whose
joining date is today or one of the previous `JOINING_DATE_WINDOW_DAYS - 1`
days (default 7 dates: on 18 Sept, 12-18 Sept). Anyone earlier is an
administrator's to add - a late record means deadlines already running or
missed, and someone senior should know. A future joining date is refused for
everybody. Same rule on the form, the bulk import (a row that breaks it is
skipped with the reason), and an edit that _changes_ the date. Refusal is a
`400 VALIDATION_FAILED` on the `joiningDate` field, matching every other
field-level refusal in this API. Test fixtures therefore use dates relative to
today, or an Admin actor, never hard-coded old dates.

**Viewer = Management: sees, downloads and prints everything, changes
nothing** (decided 2026-09-19). `VIEWER_PERMISSIONS` holds every read
permission including `document:download`, and not one writing permission. An
audit on 2026-09-19 confirmed every writing route refuses a Viewer and no
button is hidden-but-accepted by the API. Do not add a writing permission to
that list without the office asking.

Other rules worth knowing before you touch them:

- The checklist (which documents, mandatory or not, deadlines) is **decided in
  code** - `shared/src/constants/documentChecklist.ts` - not in a settings
  screen. The office asked for it that way. Migration 0025/0034 keep the table
  in step.
- The **employee code is typed** (the company's 8-digit number) and immutable;
  the identity check compares it with the code printed on the document.
- **The identity check never refuses an upload** any more (migration 0026): the
  file is stored first, read in the background, and a failure is a `Failed`
  mark HR confirms with one click. Every ID card here is a low-contrast
  photocopy; OCR failing is the ordinary case.
- **Never replace** an image already on an employee's record from MMC. A
  corrected file in MMC does not follow through - a separate decision for
  another day.
- **Reports name no employee.** `stamp-check`, `auto-stamp --report/--backlog`
  print document ids, types, outcomes - never a name, code or employee id.
  They are meant to be pasted into messages.
- **The reminder email is overdue-only**, sent by the API itself at
  `REPORT_SEND_TIME`, with the list as an `.xlsx` attachment (codes as text so
  zeros survive; `days of overdue` a number). `REPORT_INCLUDE_NOT_YET_DUE` was
  retired. `POST /api/reminders/send` no longer exists.
- **The MMC pickup** (commit `1bb772e`): the API watches
  `MMC_PHOTO_DIR`/`MMC_SIGNATURE_DIR`, takes in a photo or signature the moment
  it appears (waiting for the file to stop growing), attaches it to the employee
  on the books by code, and re-runs the stamp decision on their waiting
  documents. A sweep every `MMC_SWEEP_MINUTES` (10) is the net under the
  watcher, because a watcher on a network share can miss files. Serial queue,
  250 ms between documents. `MMC_WATCH=false` turns it off.
- **The checklist shows only "Stamped automatically" / "Partly stamped" / "Not
  stamped"**, in quiet grey, and nothing at all in report mode. No reasons on
  screen - Sameer found the reasons alarming; they live in the decision row and
  the report.

## What is done (on this branch, highlights)

Employees and checklist; document upload with background identity check
(pdf.js text layer or Tesseract OCR, eng+hin); dual signatures drawn or
uploaded; per-type placement templates with shapes; occupancy check before
stamping; stamping on upload with report/stamp modes, decisions table and
reports; MMC pickup; joining-date rule; overdue reminder with spreadsheet;
bulk employee import from xlsx; dashboard and reports; xlsx exports; TIFF/OCR
hardening (sequentialRead, errorHandler on the Tesseract worker).

Test counts at the time of writing (2026-09-22): backend unit 912, frontend
unit 167, integration 45 passing + 3 known failures (below). `npm run verify` runs lint,
typecheck, SQL safety, secret scan and unit tests.

   existed was wrong and was removed). Until each user uploads one, every HR

## How Sameer likes to work - follow this

- **Start READ-ONLY.** For anything non-trivial he asks for a plan first: what
  exists, what you would change file by file, what tests, what it might break,
  your questions. Then **STOP** and wait for answers. Do not write code until
  told "go ahead" / "build it".
- **Small steps, checks after each.** Run typecheck, lint, all unit tests, the
  integration suite. Show the results as a table. Say plainly what failed and
  why; distinguish parked failures from new ones.
- **STOP before committing.** Then, when asked, **show the commit message
  first** and wait for "OK" before committing. **Never push unless told**; he
  says "then push" or "do not push" each time. Commit messages are long prose
  explaining the reasoning, present tense, no bullet noise, ending with the
  `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>` line.
- **No migration unless he says so** - ask, and say it is a migration. He has
  approved them when the case was made (0037 StampDecisions).
- **Be blunt and own mistakes.** He values "owning the skipped suite" - if you
  missed something, say so plainly. Do not call groundwork "done".
- **Test with relative dates / admin actors**, never hard-coded old joining
  dates (the joining-date rule refuses them for HR).
- **Prove it end to end against SQL Server** for anything touching stamping:
  the integration suites in `backend/tests/integration/` are what convinced him.
- Keep the code's voice: long explanatory comments about _why_, plain English
  wording for anything HR reads, British spelling.
- Wording for HR matters to him; propose exact wording before changing screens.
- He is concise and direct. Answer what was asked; a summary he did not ask for
  annoys him.
